# 版號規則

適用於 PaperReader 的所有安裝檔、版本庫標籤與變更紀錄。

## 1. 寫法

**對外的版號**：`a.b.c`；有修正版時寫 `a.b.c.d`。四段都是不補零的十進位整數，d 為 0 時只寫三段。例：`0.1.0`、`0.1.12`、`0.1.12.3`、`1.0.0`。標籤、Release、安裝檔名、變更紀錄、「關於」頁、Android 系統設定裡看到的版本（versionName）、使用者文件，一律用這個寫法。

**工具用的版號**：Tauri、Cargo、npm 只收 SemVer 2.0.0 的三段式（四段、底線都拒收），所以設定檔裡寫成 `a.b.c` 或 `a.b.c+d`，由 `app/scripts/bump-version.mjs` 從對外的版號換算，不手寫，也不出現在任何對外的地方。

兩種寫法都**各段的意義依本規則，不依 SemVer**。

## 2. 各段的意義

| 段 | 名稱 | 什麼時候加一 | 誰決定 |
|---|---|---|---|
| c | 功能版 | **所有新功能、改動、成批的修正**都以 c 加一發布。c 是日常的發布線，位數不限（上限見第 5 節） | 維護者 |
| d | 修正版 | 某個功能版發布後才發現的錯誤：只修錯、不帶新功能、不改檔案格式時，在**最新的**功能版上 d 加一（`0.1.12` → `0.1.12.1`）。不維護舊版本的修正線 | 維護者 |
| b | 里程碑版 | c 線累積了一大批已經熟成的功能時，發布 `a.b.0`。b **不代表加了一個功能**，而是把一段時間的成熟功能定成一個穩定版 | 使用者 |
| a | 重大版 | 產品的重大轉變；1.0.0 是第一個穩定版 | 使用者 |

**進 b 的條件**（三項都要）：

1. 收進來的每一項功能都已在先前某個功能版發布過、經過使用。
2. 和前一個功能版相比只多修正，不多功能。
3. 沒有已知的嚴重錯誤。

通常要累積一大批功能。單一功能重大到足以自成一個里程碑時可以例外，但它仍要先在功能版發布過。

## 2a. 一個版本一個主題

使用者 2026-11-18：「一個版本就是一個階段更新。不要一次更新大量內容……相似、相關、相同上層的功能可以放在同一個版本更新，否則就往下累加。」

1. 每個功能版有一個主題（一句話說得出來，例如「應用內更新」「修正與反悔」），只收屬於這個主題的功能與修正。不同主題的功能各自一版，依序往下加 c。
2. 主題在開工時定；一件工作開工前先決定它屬於哪一版。
3. **每個功能在自己的工作區（worktree）與分支上開發與提交；要出它那一版時才合併進 `main`，合併後接著出版，中間不合併別的功能**。所以 `main` 一直是「已發布的版本」或「正在出的那一版」；做完但還沒輪到的功能留在自己的分支上，出版前先接上最新的 `main`、跑檢查。發布時在 `main` 上建安裝檔、打標籤。
4. 一件工作若含兩個主題，要分成兩條分支或兩組可以分開合併的提交（後一組接在前一組之上）。
5. 修正版從 `main` 出。只有 `main` 已經有下一版的功能、又要修上一版時，才從上一版的提交開 `release/a.b.c`，修、建、發，再合併回 `main`。
6. 只改開發工具、檢查腳本、文件的提交不算功能，跟著當時的版本走。
7. 修正版（d）只修那一版主題範圍內的錯。

## 3. 歸零

a 加一 → b、c、d 歸零；b 加一 → c、d 歸零；c 加一 → d 歸零。

## 4. 0.x 預覽期與檔案格式

- a＝0 的所有版本都是預覽版，Release 標「預覽版」（GitHub 的 prerelease）。0.x 的里程碑版稱「預覽里程碑」。
- **單向的格式升級**（新版寫出的資料舊版讀不了）：0.x 期間至少要隨 b 發布；1.0.0 起只能隨 a 發布。變更紀錄寫明，使用者文件寫怎麼升級。

## 5. 上限與 Android versionCode

上限：a ≤ 20、b ≤ 99、c ≤ 9999、d ≤ 99。c 到 9999 之前必須發里程碑。

**versionCode ＝ a×10⁸ ＋ b×10⁶ ＋ c×10² ＋ d**，明訂在 `app/src-tauri/tauri.conf.json` 的 `bundle.android.versionCode`（Tauri 預設的算法會丟掉 d）。最大值 2,099,999,999，不超過 Android 的上限 2,100,000,000。已發布的 0.1.0 是 1000（Tauri 預設算法），之後的版本都比它大。

| 版號 | versionCode |
|---|---|
| `0.1.0`（已發布，舊算法） | 1,000 |
| `0.1.1` | 1,000,100 |
| `0.1.1.1` | 1,000,101 |
| `0.2.0` | 2,000,000 |
| `1.0.0` | 100,000,000 |

## 6. Windows

版號照原樣給 Tauri；檔案版本與 MSI 的版本由 Tauri 自動成為 `a.b.c.d`。

## 7. 標籤、發布與檔名

- git 標籤：`v` 加對外的版號，例 `v0.1.12`、`v0.1.12.3`。
- Release 標題：`PaperReader 版號`；里程碑版加「（里程碑）」，0.x 加「（預覽版）」。每次發布都明確指定為最新版。
- 安裝檔名：`PaperReader-版號-架構.apk`（對外的版號）。
- Android 的 versionName 設成對外的版號（在 `gen/android/app/build.gradle.kts` 覆寫 Tauri 給的值）；「關於」頁顯示對外的版號。

## 8. 變更紀錄

`CHANGELOG.md` 照 Keep a Changelog：每一版一節，標題 `## [版號] - 日期`。里程碑版那一節先寫一段摘要，列出收錄了哪些功能版。撤回的版本標 `[YANKED]`。

## 9. 一致性

`tauri.conf.json` 的 `version`、`app/Cargo.toml` 工作區的版號、`app/package.json` 的 `version`（三處都是工具用的寫法）必須相同；Android 覆寫的 versionName 必須等於對應的對外版號；`bundle.android.versionCode` 必須等於第 5 節的公式。`app/scripts/check.ps1` 檢查，不一致就不通過。
